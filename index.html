Ember, Knowledge Graph for AI Coding Agents

With Ryan Stoffel, Elijah Tabor, Brandon Magana & Jacob Pugh  ·  California Baptist University Senior Capstone  ·  Fall 2026 to Present

Ember replaces static context files like AGENTS.md with a typed knowledge graph of a team's decisions, conventions, people, tickets, and code. The graph updates itself from GitHub, Jira, and Slack activity and is exposed to any AI coding tool through an MCP server. A web dashboard shows the team where its tools disagree, such as a blocker mentioned in Slack that Jira never recorded.

Read moreShow less

Dashboard

The dashboard reads every connected source and surfaces where they don't add up. The Needs attention list groups problems into blockers, failing checks, status drift, work waiting on review, missing links, and decisions that never made it into a ticket. Each one shows the Slack message, ticket, and pull request behind it, along with a one-click fix such as flagging a ticket as blocked, re-running checks, or moving a ticket back to In Development. A Work in flight table lists every open ticket with its pull request and where it was last discussed, next to a recent activity feed across all sources.

Knowledge graph

  • An interactive force-directed graph of work items, changes, messages, people, decisions, conversations, and code modules, filterable by source and node type.
  • Group by source pulls the GitHub, Jira, and Slack subgraphs apart. People resolved across all three sit in the middle, so selecting a ticket shows the typed relationships that connect it to pull requests, messages, and teammates.
  • A preview workspace with a made-up team lets anyone try the full app before connecting real sources. Changes made there stay in the browser.

Architecture and infrastructure

  • Ingestion services receive GitHub App webhooks, Jira webhooks, Slack Events API events, and GitLab webhooks, and a pipeline writes them into Neo4j as typed nodes and relationships.
  • An MCP server exposes the graph to AI coding tools, alongside a Next.js web app and a CLI in the same monorepo.
  • Runs on a homelab k3s cluster provisioned with Ansible and deployed GitOps-style with Flux. Secrets are encrypted with SOPS, services are reached over Tailscale, and CI publishes container images to GHCR.
  • Every branch and pull request maps to a Jira ticket, and design choices are recorded as Architecture Decision Records.

Formula Fly, a Connectome-Wired Fruit Fly That Drives

With Ryan Stoffel, Elijah Tabor & Joseph Rus  ·  CSCI 4220 Machine and Deep Learning  ·  September 2026 to Present

A fully simulated tethered-fly rig. A virtual fruit fly sees a race track through a visual system wired like the real fly connectome, models of its brain circuits turn that into movement of a simulated body, and those movements drive a race car. The fly learns to drive with reinforcement learning. The research question is whether biologically copied wiring helps, hurts, or doesn't matter compared with unconstrained networks of the same size.

Read moreShow less

Pipeline

Eye, brain, body, car. The eye is the flyvis optic-lobe model, built on the FlyWire adult brain connectome. Its activity feeds models of the fly's brain circuits, which move a flybody fly in MuJoCo, and those movements become steering, throttle, and brake. Every stage sits behind one shared interface (a camera frame in, a control vector out), so any stage can be swapped for a simpler stand-in. A direct-drive agent skips the body entirely. The connectome's topology stays fixed, and the team trains the encoding, decoding, and optionally the synapse strengths with PPO in PyTorch.

Practice track and demo

  • The scientific benchmark is the team's own MuJoCo practice track, built from Silverstone's centerline. The camera sits at the fly's head because flyvis models motion vision: the eye needs to see the scene expand as the car accelerates and flow sideways as it turns.
  • The second clip shows that view. The colored hexagons are the activity of the fly's visual neurons while driving, followed by the raw image as the fly's compound eye samples it.
  • A HUD shows speed, RPM, gear, steering, suspension travel, and a live track map. Laps are timed with penalties for leaving the circuit and logged automatically. A human can drive the same track with a keyboard or gamepad for comparison.
  • The headline demo, shown in the first clip, puts the fly in the cockpit of a Formula car in Assetto Corsa on the same circuit.

CBU WebTAK, Live Campus and Airport Flight Map

September 2026

A 2D/3D mapping server of the CBU campus and Riverside Municipal Airport (KRAL). It tracks CBU flights around campus and gives details about the area, with every live feed delivered through TAK (Team Awareness Kit) using FreeTAKServer.

Read moreShow less

Data flow

A Python feeder polls ADS-B data for CBU's aircraft and sends each one to FreeTAKServer as a Cursor on Target (CoT) event, carrying registration, position, altitude, speed, heading, and aircraft type. A FastAPI backend connects to the same server as a TAK client and serves the latest aircraft to the browser, where MapLibre GL JS draws them over OpenStreetMap campus buildings (tiltable into 3D) and airport geometry. The map takes data only from TAK, never directly from the public feeds, so it reflects exactly what the TAK network sees.

  • More TAK feeds. Separate feeders push KRAL weather from NOAA's Aviation Weather Center and live Riverside Transit Agency buses from its GTFS-realtime feed, using the same pattern.
  • Debugging the relay. FreeTAKServer only forwards a client's events once that client has announced itself with a self-presence message. Measured directly, an unregistered sender delivered zero events. Both ends now register on connect and re-announce every two minutes.
  • Deployment. FreeTAKServer runs in Docker, and every service runs under systemd with automatic restarts, grouped so one command starts or stops the whole stack. Caddy serves it over HTTPS with Let's Encrypt certificates.

SnapDose, AI Diabetes Nutritionist

With Ryan Stoffel, Elijah Tabor, Micah Suk & Millie Anderson  ·  California Baptist University  ·  January to May 2026

SnapDose helps diabetes patients count carbs instantly: snap a photo of a meal and get an AI carbohydrate estimate in seconds instead of spending 5 to 10 minutes on manual calculation. It tracks meal history, shows a confidence rating for each estimate, identifies food items in photos, and monitors weekly trends. By making carb counting fast and easy, SnapDose helps patients make better food choices and manage their blood sugar more effectively.

Read moreShow less

Architecture

SnapDose runs on a serverless Google Cloud Platform architecture. The React Native frontend uses Firebase Authentication and Firestore, with security rules keeping each user's data private. When a user uploads a meal photo, Firebase Storage triggers a Google Cloud Function that sends the image to the Google Gemini 3.1 Pro API with specialized nutrition prompts. Gemini returns carb estimates, confidence levels, detected foods, and notes, which are saved to Firestore with timestamps as a JSON file. The app caches data locally through Firestore's offline persistence.

A Spring Boot REST API bridges the app to a simulated physical insulin pump built on a Tab5 microcontroller. When a user logs carbs and requests an insulin dose, the request is sent securely through Firebase Authentication to the Spring Boot API, which relays it to the Tab5 device. The Tab5 pump polls for pending bolus requests, delivers insulin, reports confirmation to Firestore, and maintains heartbeat communication. SnapDose also integrates the Dexcom API to pull real-time continuous glucose monitoring data, so users can view blood sugar alongside meal tracking and insulin dosing in one unified dashboard. The entire system is serverless and scales automatically, with all user data stored securely and controlled by the user.

System architecture on Google Cloud Platform

Screens

  • Home and Dashboard (shown above, in dark mode). Lets users calculate and log an insulin dose. It displays the current insulin on board (3.0u active) and offers two dose types, Meal Dose and Correction Dose. Users can adjust total carbohydrates with plus and minus buttons, and the app calculates a recommended dose based on their carb ratio and active insulin.
  • Insulin Dosing. Calculates insulin requirements for meals based on carbohydrate intake and current insulin activity. Users can quickly adjust carb counts and choose between meal-based dosing (using carb ratio) or correction dosing (targeting a specific glucose level).
  • Dose Confirmation Sheet. Validates dosing calculations before delivery by showing the complete mathematical breakdown. It protects against accidental doses with a slide-to-confirm interaction, and displays how current glucose, carb ratio, and active insulin combine to determine the final dose amount.
  • AI Analysis Results. Processes food photos through AI to identify items and estimate carbohydrate content. Confidence ratings help users decide whether to accept the estimate or adjust it manually, and the screen streamlines the transition from carb estimation to insulin dosing.
  • Weekly Summary. Aggregates meal and carbohydrate data to reveal eating patterns over time. Users can review past meals with visual thumbnails and timestamps, and use it as a searchable log of what was eaten and when insulin was dosed.
  • Settings. Manages connections to external diabetes devices (CGM and insulin pump) and monitors device connectivity so data keeps flowing. Users can configure or change their insulin delivery device and verify pairing status.
  • Profile. Stores the diabetes management parameters that drive dose calculations, including target glucose ranges, physical characteristics, and carb-to-insulin ratios. It is the central place to review and adjust personalized treatment parameters.

Wedding Website, Event Site with RSVP System

May to October 2026

A custom-built, responsive wedding website hosted on Netlify. Guests can find the event details, day-of schedule, photos, and registry links, and RSVP online. Every response is emailed automatically, and a serverless function keeps a running guest count.

Read moreShow less

RSVP and email pipeline

The RSVP form collects the responding guest's name, whether they are attending, the full name of each guest in their invited party (with a live head count as they type), a phone number, and a mailing address. On submit, the browser first sends the guest count to a Netlify Function, which adds it to a running total stored in Netlify Blobs and returns the new total. The browser then sends the full RSVP to Web3Forms, which emails it to the couple with a generated subject line such as Wedding RSVP: Jane Doe (3 attending) - 57 guests total. If the counter is ever unavailable, the RSVP still goes through without the total.

  • Secret handling. The Web3Forms access key is never committed to git. A Netlify build step injects it into the page from an environment variable at deploy time.
  • Inbox automation. Every RSVP email carries a reference tag that a Gmail filter uses to file it under its own label automatically. An optional Google Apps Script syncs that label into a spreadsheet that serves as the authoritative guest count.
  • Admin reset. A token-protected endpoint on the same function resets or corrects the running total after testing.
  • Registry. A dialog lets guests choose between the gift registry and a honeymoon fund page.

Design and performance

  • Node.js scripts using sharp resize and compress the photos and key out the backgrounds of public-domain botanical illustrations and hand-painted artwork.
  • The vine border around each card is an SVG generated by a script, drawn as a 9-slice border image so it tiles cleanly at any size.
  • Netlify config sets long-lived cache headers for images, security headers, and a redirect for old links.

A golf tracking mobile app built with Flutter/Dart and Firebase. It uses GPS positioning and the Google Maps SDK to help golfers track shots, distances, and rounds on real courses with live location data, plus a social feed for friends.

Built with Flutter/Dart and Firebase, the app uses GPS positioning and the Google Maps SDK to help golfers track their shots, distances, and rounds on real courses with real-time location data. Firestore handles real-time data syncing, SharedPreferences stores local game state, and Firebase Storage manages media. Social features such as friend requests, likes, and comments run through Firestore streams, with Firebase Authentication handling user management.
